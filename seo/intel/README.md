# Content Intelligence

Система, которая оценивает 202 страницы стран по измерениям, а не по мнению модели.

## Зачем она заменила Quality Score

Внутренний Quality Score отвечал на вопрос «похоже ли, что текст писал человек».
Это была правильная метрика ровно до появления трафика. После — вредная: красиво
написанная страница может не ранжироваться, а невзрачная приносить выручку, и
оценка 100/100 у страницы без единого показа дезориентирует.

Полнота контента осталась, но весит 5 баллов из 100.

## Главное правило

**Отсутствие данных — это не ноль.**

Компонент без источника не участвует в оценке: его вес убирается из знаменателя,
а не подставляется нулём. Если измеримо меньше 40% веса, оценки нет вообще — стоит
`—`, а не `D`. Панель, которая ставит двойку странице без подключённого API,
отправляет редактора переписывать текст, когда чинить надо доступ.

## Из чего считается Performance Score

| Компонент | Вес | Источник | Условие участия |
|---|---|---|---|
| CTR относительно позиции | 25 | Search Console / Вебмастер | ≥100 показов |
| Позиция | 15 | Search Console / Вебмастер | ≥100 показов |
| Конверсия | 25 | Метрика + заказы | ≥30 заказов **во всём корпусе** |
| Выручка | 15 | заказы | есть привязка |
| Вовлечённость | 10 | Метрика | ≥50 просмотров |
| Свежесть | 5 | профиль | всегда |
| Полнота контента | 5 | профиль | всегда |

Оценки: **A+** ≥85 · **A** ≥72 · **B** ≥58 · **C** ≥42 · **D** <42 · **—** данных мало.

CTR судится **относительно позиции**. 1.2% на 28-й позиции лучше, чем 4% на второй.
Абсолютный CTR отранжировал бы корпус по тому, как он уже ранжируется.

Выручка логарифмическая: линейная дала бы всем, кроме одной страны, ноль.

## Статусы

`Locked` → `Draft` → `High Performer` → `Needs Improvement` → `Stale` → `Reviewed` → `Published`
(первое совпадение выигрывает).

- **High Performer** — CTR ≥1.2× ожидаемого для позиции, позиция ≤10, конверсия не
  ниже медианы. Плюс ворота: ≥300 показов и ≥20 кликов. Ворота важнее порогов —
  повысить страницу по 12 показам значит заморозить её навсегда.
- **Needs Improvement** — минимум **два** независимых плохих сигнала. Один — это шум
  или сезон; требование двух не даёт очереди стать всем корпусом.
- **Stale** — просрочен `next_review` или прошло больше 180 дней.
- **Locked** — решение человека, живёт в профиле и коммитится: `node seo/intel/lock.mjs <slug> "причина"`.

## Что нельзя переписывать автоматически

`Locked`, `High Performer`, топ-10 по выручке, топ-10 по конверсии, топ-10 по CTR.

Порог асимметричный намеренно: переписать зарабатывающую страницу стоит реальных
денег и обнаруживается через недели, а не переписать — стоит задержки.

Топы **не считаются**, пока в корпусе меньше 30 заказов и нет поисковых данных:
иначе «топ-10 по выручке» — это «все, у кого была хоть одна продажа».

Запрет не убирает рекомендации, а снимает только автоприменение.

## Приоритет редактора

Не по размеру страны, а по потенциалу:

```
недополученные клики = показы × (ожидаемый CTR для позиции − фактический CTR)
```

взвешенные по выручке там, где она привязана. Ниже 5 недополученных кликов —
не задача.

## Источники

**Tier 1 — факты.** Search Console, Яндекс Вебмастер, Яндекс Метрика, заказы Magic eSIM,
каталог Magic eSIM, Apple/Google/GSMA, операторы, госисточники.

**Tier 2 — только интент.** Reddit, vc.ru, DTF, форумы. Показывают, какие вопросы
задают. Ответы оттуда не переносятся.

**Tier 3 — не используются.** SEO-помойки, AI-сайты, скраперы. Верный факт с
Tier 3 всё равно не годится: его надо найти там, где за него отвечают.

## Атрибуция

```
страница страны → checkout → заказ → выручка → прибыль
```

Сегодня замкнуто до `country_code`: выручка **на страну** считается честно.
Не замкнуто — **канал**: заказ с `country_code=TR` мог прийти со страницы Турции,
с лендинга или по прямой ссылке.

Метка происхождения уже ставится страницами в `sessionStorage`. Осталось
пробросить её в создание заказа и добавить колонки — миграция подготовлена в
`~/esim-backend/scripts/migrations/2026-08-attribution-page.sql.NOT-APPLIED`
и **не применена**.

Цели Метрики на сайте уже настроены — все 23 и все действительно вызываются:
каталог, поиск страны, `country_tariff_click`, `tariff_buy_click`, `checkout_open`,
`payment_sbp_click` / `payment_card_click`, `payment_success` / `payment_failed` /
`payment_canceled` / `payment_tech_error`, промокоды. Новых целей не требуется.

**Воронка на страницу считается в Метрике и без миграции.** Разбивать достижения
целей по `ym:pv:URLPathFull` бесполезно: клик по тарифу происходит на странице
страны, а оплата — на лендинге и на payment-success, и по URL они к странице не
привяжутся. А вот по **`ym:s:startURL`** — странице входа в визит — привяжутся все
шаги сразу, потому что это свойство визита, а не отдельного просмотра.

Миграция всё равно нужна: Метрика даёт визиты и цели, но точные деньги и прибыль
живут в `retail_orders`, и связать их с заказом можно только меткой в самом заказе.

## A/B

Две разные методики, смешивать нельзя:

- **SEO** (title, description, H1) — одновременного сплита не бывает, поисковик видит
  одну версию. Работает последовательный тест **с контрольной группой**: из своего
  изменения вычитается общий дрейф корпуса. Без контроля декабрьский рост CTR у всех
  запишется себе в заслугу.
- **Конверсия** (CTA, первый экран) — настоящий сплит на клиенте.

Автопубликации нет ни в одном режиме. Тест также показывает, если вариант выигрывает
по конверсии и проигрывает по деньгам.

## Команды

```bash
node seo/intel/collect.mjs          # собрать всё доступное
node seo/content-dashboard.mjs      # таблица + снимок дня
node seo/intel/center.mjs           # Content Intelligence Center (вне репозитория)
node seo/intel/lock.mjs --list
```
